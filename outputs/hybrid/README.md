# 双模型自动游玩控制器

规划模型负责路线、抓牌、事件、商店、休息、升级和移除；战斗模型负责战斗出牌、目标、药水及战斗内选牌。单一合法动作、继续按钮及奖励领取由程序执行。两者共用 STS2MCP。配置模板使用 DeepSeek API 的 `deepseek-flash` 和 TypeSafe API 的 `jev-latest`，也可以在桌面应用中分别更换提供商、接口、密钥和模型。

## 配置

首次运行读取 `config.example.json`；桌面应用保存设置后生成本机 `config.json`，命令行也可复制模板后编辑。两者可分别配置 `provider`、`protocol`、URL 和模型 ID。规划模型的 `reasoning_effort` 默认显式设为 `low`，同时用于战略决策与局后复盘，可在桌面应用中改为中或高。OpenRouter Jev 的 `decisions` 协议使用 `https://openrouter.ai/api/alpha/decisions`；普通聊天协议使用 `/api/v1/chat/completions`，二者的请求格式不能混用。密钥不写入源码或配置文件；桌面应用可按职责和提供商地址保存到当前用户的 Windows 凭据管理器，命令行默认分别读取 `SPIRE_PLANNER_KEY` 与 `SPIRE_COMBAT_KEY`。

`chat_schema` 使用 Chat Completions + JSON Schema，`chat_json` 使用 JSON Object，`decisions` 使用 Jev Decisions 接口。规划模型支持前两种；战斗模型支持三种。供应商必须支持所选格式，否则控制器停止并报告。

## 完整牌组 Mod

仓库的 `../../vendor/STS2MCP` 源码在兼容性修复基础上增加 `player.deck`；发布仓库不包含已编译 DLL。永久牌组复用手牌的卡牌序列化逻辑，提供卡牌 ID、名称、已解析说明、升级、费用、类型、稀有度、关键词、附魔、苦痛及 `deck_index`；它不是手牌或抽牌堆的近似统计。`deck_index` 只表示本次状态中的牌组位置，不是跨状态稳定的卡牌实例 ID。

按照 [Mod 构建说明](../../vendor/STS2MCP/LOCAL.md)编译后，退出游戏，将改版 Mod DLL 与清单安装到游戏的 `mods/` 目录，再重新打开游戏。`require_full_deck` 默认开启；非战斗状态缺少完整牌组时停止，不让规划模型在信息不全的情况下选卡。

## 启动与停止（PowerShell）

1. 确认旧 Jev 单模型控制器已停止，避免两个程序同时操作游戏。
2. 从 Steam 打开游戏，可自行选角色开局，也可停在主菜单继续已有存档。没有存档时控制器默认选择铁甲战士。
3. 运行 `./start.ps1`。脚本根据配置读取两组密钥环境变量，缺失时分别提示隐藏输入。
4. 运行 `./stop.ps1` 停止。游戏保持开启，控制器在本局结束后自动退出，不自动开始下一局。

`python hybrid_player.py --check` 只读检查，不调用模型、不发送游戏动作。

日志在 `runs/<时间>/`：

- `events.jsonl`：模型响应、耗时、游戏动作与结果。提供商响应中的费用字段会在写入前删除。
- `run-memory.sqlite3`：本局事实账本。完整保存每次观测、当时合法动作、模型选择、检索到的跨局记忆、实际动作及返回结果，并用 UUID 关联“观测 → 决策 → 动作 → 后续观测”。动作会明确标为已观察变化、观察未变化、被游戏拒绝或仍待后续观测。
- `memory.json`：版本 5 的有界工作记忆。`plan` 是规划侧计划；`planner.decisions` 保存最多 40 个战略决定，`planner.battle_reports` 保存最多 24 份战斗结果交接；`combat` 只保存当前战斗最多 30 个紧凑观测和 30 个动作，以及出牌、药水、轮次和生命样本汇总。
- `latest_state.json`：最近局面。
- `result.json`：本局结束结果；`status.json`：异常停止原因。
- `stdout.log` / `stderr.log`：后台运行日志。

中断后继续同一局：`./start.ps1 -RunDir '原来的日志目录'`。新开一局不要复用旧目录，以免带入旧计划。异常退出遗留 `controller.lock` 时，先确认旧进程已结束，再手动删除该锁文件。

## 分工和限制

规划模型每次战略选择时更新一份简短计划；战斗模型每步都收到该计划和当前真实局面。战斗优先生存，计划不会强迫战斗模型为未来保留药水而当前送死。规划器不参与逐张出牌。内部职责标识固定为 `planner`、`combat`、`both`，不随当前提供商或模型名称变化。

行动前再次读局面，状态变化则丢弃旧选择；停止标记在模型调用返回后再次检查。游戏动作超时不会自动重试，因为动作可能已执行。模型请求可重试。未知界面、无进展、模型返回非法选项、达到调用上限都会停止。

规划模型只收到战略决定和战斗结束后的结构化结果交接：敌人、胜负、战前/战后资源、观测到的轮次、净生命变化及战后战略状态。它不接收逐步战斗观测、手牌历史、出牌顺序、用牌次数或药水操作。相同永久卡牌合并为带 `count` 的条目。默认按 1,000,000 token 总上下文计算，为输出保留 32,768 token，并另留 8,192 token 协议开销；超出输入预算时依次移除较大的旧历史分区。战后血量可能包含回复、被动效果和自伤，`net_hp_change` 不是精确受伤量。

战斗模型收到当前完整局面、规划侧计划、本场紧凑观测与动作，以及最多 5 个同角色、同版本范围、敌人匹配的历史战斗案例。案例只含可观察事实和数据限制，不把单次结果包装为因果规则。默认按 65,536 token 总上下文计算，为聊天协议输出保留 16,384 token，并另留 4,096 token 协议开销。TypeSafe `decisions` 协议不接受本地输出上限字段，但采用相同预留计算输入。服务端仍报告 `max_tokens_exceeded` 时会将可选历史预算减半并只重试模型请求一次，不会发送游戏动作。自动执行的战斗动作也只写入战斗分区。检测到战斗结束提示、战后界面或终局后，生成战斗案例、向规划侧交接经过清理的结果，并立即清空本场战斗记忆。战斗内选牌不会清空；未知过渡界面不视为战斗结束。版本 5 不迁移旧工作记忆，继续旧对局时会从当前局面重新建立。

`planner_context_tokens`、`planner_max_output_tokens`、`combat_context_tokens` 和 `combat_max_output_tokens` 可在 `config.json` 调整。发送前使用保守的 Unicode 字符数估算 token；供应商响应中的 `usage` 才是实际计数。

这里的本场记忆由控制器按事实记录和裁剪，模型通过后续请求读取；Jev 的 `decisions` 响应只给动作选择，因此系统不会凭空补写战斗模型的自由文本理由。`run-memory.sqlite3` 保留完整关联事实，`memory.json` 只是可丢弃、可重建的工作集。系统不请求、估算、累计或展示 API 费用；提供商响应中附带的费用字段会在日志和事实账本写入前删除。

这套分工不保证更高胜率。应固定角色、进阶、游戏/Mod 版本和种子做多局对比，分别统计胜率、到达层数、战斗损血和耗时。

验证命令：`python -m unittest discover -s . -p 'test_*.py' -v`。

## 跨局记忆（默认开启）

跨局记忆分为两个互不混写的来源：

- 规划记忆：本局 `game_over` 后由规划模型读取战略动作、战斗结果交接和清理掉战斗字段的最终状态，生成最多 8 条带证据引用的条件假设。程序校验引用存在，但不会把模型解释标记为已证实事实。
- 战斗记忆：每场战斗结束时由控制器把本场可观察事实直接写成结构化案例，包括敌人、胜负、资源端点、轮次、动作计数、出牌计数、药水使用和数据质量说明。它不调用额外模型，也不生成无法从日志验证的战术结论。

规划复盘看不到战斗案例中的逐步动作和汇总；战斗检索也不会读取规划模型的复盘经验。旧日志缺少完整关联时不会推测性重建战斗案例。

长期经验保存在 `experience/lessons.sqlite3`。每局另外输出 `review.md`（可读复盘）、`review.json`（含证据）和 `review_status.json`。同一日志目录的 run_id 固定，重复执行复盘不会重复入库，也不会对已入库的局再次收费。

下局自动检索同角色、同 `memory_scope` 的记忆，每次最多 5 条。`planner` 只按当前界面检索规划假设；`combat` 只按当前敌人的标准化 ID 检索战斗案例，敌人实例编号变化不会阻断匹配。检索结果写入 `events.jsonl`，并同时随决策保存在本局事实账本。规划建议会去重，但相互矛盾的假设不会被自动判定为已经解决。当前采用结构化条件过滤，不是向量数据库，也不会训练模型权重。

配置项：

- `cross_run_memory`：总开关。
- `experience_db`：数据库路径，相对本程序目录解析。
- `memory_scope`：游戏/Mod 版本隔离标签。升级游戏或改变主要 Mod 后应修改该标签，以免旧机制经验混用；不是自动检测出的游戏版本。

复盘请求失败、缺少密钥或达到调用上限时，对局结果保留，状态标为 `pending`。可设置 API Key 后补跑（不连接游戏、不执行游戏动作）：

```powershell
python hybrid_player.py --review-only --run-dir 'runs/对应局目录'
```

若之前执行过 `stop.ps1`，需先删除本目录 `STOP` 标记才能补跑。人为中断或程序错误不会自动写成“输掉一局”的经验；只有有完整终局结果且有动作日志的局才入库。旧单模型日志可能混合多局，当前不自动导入，以免把不同角色或不同局的记录串在一起。

复盘会多产生一次规划模型请求；调用次数记入 `memory.json` 的 `review` 项。新局继续使用新的日志目录，跨局经验由共享数据库传递，不应复用上一局的 `memory.json`。共享数据库包含 `reviews`（规划假设）和 `combat_cases`（战斗事实）两张逻辑分区，桌面应用会分别标记为“规划”和“战斗”。
